The human chose to probe stage first. A one-off probe, not committed, used mentors A and B.
It read the current-month rows through the stats API after each action:

| After | A: open / closed «ДЗ» | B: open / closed «ДЗ» |
|---|---|---|
| A replied | 1 / 0 | — |
| reassigned to B | 1 / 0 | 1 / 0 |
| B closed | 0 / 1 | 0 / 1 |

**Stage matches the story.** The spec asserts "both mentors". That makes PRJ-TC-69 wrong in steps 8 and
22–24. The test case is read-only for the agent. **For the human:** fix steps 8 and 22–24 in AIO to
match AC3. There is no product bug to file, because the product does what the story says.

Side effect of the probe: it answered and closed one pending homework on «Трейдинг основы». Diagnostics
later showed that pending homeworks there belong to autotest students (`test-student-…@example.com`),
not to real users. The committed spec creates its own student for every scenario.

## 5b. After the fixes: stage disagrees on the 10-character boundary

The green run after the fixes gave 1 and 2 passed, 4 skipped, and **3 failed**:
`answersHomework should change by 2 (baseline 19, current 22)`. All three messages counted, including
«Дякую, ок!», which is exactly 10 characters. Earlier a 7-character message did not count, so the
backend counts text length without HTML, and the boundary is **≥ 10**.

Triage per `bug-report`:

- Re-run with `--repeat-each=3 --workers=1`: 3/3 red. Two failed on the assertion, the same way
  (+3 instead of +2). One hit `ECONNRESET` after 34.6 minutes: environment, a network or VPN drop.
- Duplicate search, read-only JQL: no open bug. The related **PRJ-2848** (done 2025-09) has the expected
  result «Відповіді **менші за 10** символів **не** зараховуються», which allows exactly 10.
- **Verdict: not a clear product bug.** The requirements conflict. Story PRJ-2288 AC5 and TC-69 step 12
  say «> 10». PRJ-2848 implies «≥ 10», and stage behaves like PRJ-2848. Per the skill, the agent does not
  guess towards "product bug" and asks the human. At this point, there is no bug draft yet.

**Human decision (2026-09-30).** Treat it as a bug against PRJ-2288. The draft is
`docs/bugs/2026-09-30-otvety-dz-10-simvolov.md`, with PRJ-2848 noted as the conflicting source. Test 3 now
sends the messages one at a time and checks after each one:

- 11 characters: must count. `shouldSeeStatsDelta` checks it.
- exactly 10 characters: must **not** count. This uses `shouldSeeStatsHold`, which rereads the row for
  15 s. `toPass` cannot prove an absence.
- 37 characters: must count.

Each check names the product meaning in its failure message. On stage it now fails on the 10-character
step:
`Повідомлення рівно з 10 символів («Дякую, ок!») ЗАРАХОВАНО у «Ответы ДЗ» … changed by 2, expected 1`.

Test 4 was first marked `test.fixme`. Then **the human decided not to automate the previous-month check
at all**. The test was removed, together with `shouldSeeStatsUnchanged` and
`DateHelper.getKyivPreviousPeriod`, which only it used. The human filed the bug as
[PRJ-6789](https://jira.example.com/browse/PRJ-6789). Test 3 was added to `ci/known-failures.json`
(job `admin-stage-regression-tests`), so Jenkins lists it as `known` instead of `new`.

Two things the evidence collector got wrong, both found in this triage and fixed:

- `collect-evidence.mjs` reported the **first** failed step. Allure also marks a step failed when a
  `toPass` retry inside it failed and a later attempt passed. The script now reports the **last** failed
  step, where the test actually stopped.
- `test.beforeAll(() => linkTestCase(…))` attached the TMS link only to the first test the worker ran:
  tests 2 and 3 had no PRJ-TC-69 link. The spec now links in `beforeEach`. Before, `ui-autotest` recommended
  `beforeAll`. Now it forbids it.
