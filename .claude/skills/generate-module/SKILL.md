# Generate module code (`demo/modules/<id>/`)

Stage 2a of "creating a new module" (host side; the emulator side is `generate-emulator` Part B, the whole chain is
run by `create-module`, `docs/modules/README.md` "Lifecycle"). Reads one module's specs - `development/<name>/specs/module.yaml`,
`module.service.yaml`, `module.service.md` - as the **source of truth for data** (names, requests, mapping) and
generates code that follows the **project rules** for everything the specs don't decide: `AGENTS.md` "Module
architecture" and "Code design", `docs/architecture/code-design.md`, `docs/architecture/ddd-yii2.md` (rule
`.claude/rules/ddd-yii2.md`), `docs/modules/README.md`, the `yii2-*` skills. If a spec and a rule contradict each
other, stop and ask. The procedure follows skill **`code-generation`**; review by **`design-review`** (maker ≠
checker, spawn a fresh subagent).

Input: the module name (`<name>` = `<id>`, `module.yaml` → `module.name`). Read the specs with `yaml-read` before
generating anything.

Run from the repository root; PHP commands inside `php-cli` (`MSYS_NO_PATHCONV=1 docker compose exec -T -w /app/demo
php-cli ...` in Git Bash).

## Logging
Log every step with skill **`init-log`** into `<log dir>/log_generate-module.log` (JSON line: `action`, `start_time`,
`end_time`, `execution_time`); create a log dir of your own if not given one (`bash .claude/skills/init-log/init-log.sh
start`). Steps: `check preconditions`, `read specs`, `generate domain`, `check domain`, `generate application`, `check
application`, `generate infrastructure`, `yii migrate`, `check infrastructure`, `generate interface`, `check
interface`, `register module`, `unit tests`, `design-review`. A failed step is logged as `FAILED: <action>`.

## 1. Preconditions
- `demo/vendor/autoload.php` exists and `php yii help` runs (`init-project`/`init-api`); the host's own process tracking
  (`demo/domain/process`, `demo/application/process`, `demo/controllers/BaseController.php`) exists - else stop, this
  skill never creates host code, only module code.
- `development/<name>/specs/module.yaml` and `module.service.yaml` exist and pass `yaml-analyze` with no errors; else
  stop and name what is missing/invalid (run `create-module` first).
- `demo/modules/<id>/` does not exist yet. If it does, compare every file this skill would write against the specs
  (same rule as generate-api §2): missing → generate; present and equal in substance → keep; different → **never
  overwrite**, list the differences and ask.

## 2. Layout generated

```text
demo/modules/<id>/                            namespace app\modules\<id>
    Module.php                           extends yii\base\Module, implements yii\base\BootstrapInterface
    controllers/V1Controller.php         extends app\controllers\BaseController
    application/<Method>UseCase.php      one per service_methods[] entry that needs one (see §3.2)
    domain/RemoteServiceClient.php       interface: send(string $path, string $httpMethod, array $body): array
    domain/StatusMapper.php              pure: maps a remote status value to Status::Success|Process|Fail per method
    domain/RequestBodyBuilder.php        pure: builds the remote body from `data` + callback_url per method (module.service.yaml mapping)
    domain/<Entity>.php + domain/<Entity>Repository.php     only per migrations.extra_tables[] with entity.generate: true
    infrastructure/CurlRemoteServiceClient.php   implements RemoteServiceClient (PHP curl, no new Composer dependency)
    infrastructure/Ar<Entity>.php + infrastructure/Ar<Entity>Repository.php   only for extra tables
    migrations/M<ts>RegisterService.php  mandatory (AGENTS.md "Service registration")
    migrations/M<ts><ExtraTable>.php     one per migrations.extra_tables[]
demo/tests/Unit/modules/<id>/domain/, application/    unit tests (fakes, no database - same pattern as generate-api §"Tests")
```

## 3. Generate layer by layer (inside out)

For each layer, read the two YAML specs and `module.service.md` completely before writing; write only missing files (or
ones the user agreed to regenerate, §1); run `php -l` on every written file
(`MSYS_NO_PATHCONV=1 docker compose exec -T -w /app/demo php-cli php -l <file>`); continue only when checks pass.

### 3.1 Domain (`demo/modules/<id>/domain/`)
- `RemoteServiceClient` interface: one method `send(string $path, string $method, array $body): array` (decodes JSON,
  throws on transport/HTTP error - the module's use case catches it and reports `fail`/lets `doProcess()` throw per
  `getCallbackStatus()`/`doProcess()` contract in AGENTS.md).
- `RequestBodyBuilder`: one pure method per `service_methods[].name`, building the remote body from the init `data`
  (per `remote_request.body.params[].from`/`value`) **and always appending** `callback_url` =
  `http://demo.dev/<id>/v1/callback` (flow.md §1a - never read from `data`, never omitted).
- `StatusMapper`: one pure method per method mapping a remote status value (`status_param` path) to `Status::Success`/
  `Process`/`Fail` per `remote_request.response.status_map` (`default_status` as the fallback; a value that resolves to
  neither `default_status` nor a listed one has no valid mapping - this is a spec error, not a runtime case: caught by
  §5's check, not generated as a runtime branch); a second method per method with a `callback` block does the same for
  `callback.status_map`.
- One domain entity + repository interface per `migrations.extra_tables[]` with `entity.generate: true`, columns as
  declared - same pattern and rules as `demo/domain/process/Process.php` (pure PHP, no Yii - `docs/architecture/ddd-yii2.md`).
- No Yii, no `Yii::$app`, no ActiveRecord, no infrastructure classes (checked in §4, same grep as generate-api).

### 3.2 Application (`demo/modules/<id>/application/`)
- One use case per `service_methods[].name` needing orchestration beyond pure mapping: takes the init `data`, calls
  `RequestBodyBuilder`, calls `RemoteServiceClient::send()` (constructor-injected interface), reads
  `external_id_param`/`status_param` from the decoded response, calls `StatusMapper`, returns
  `['externalId' => ?string, 'status' => Status, 'response' => array]` for `V1Controller::doProcess()` to apply to the
  `Process` entity it received. A second use case (or a second method) handles the callback body the same way via
  `callback.status_map` when the method has a `callback` block.
- Depends only on the domain layer (interfaces) - no Yii, no ActiveRecord (checked in §4).
- Skip a use case class for a method with no logic beyond a single mapping call **only if** the resulting class would
  be a pure pass-through with no branching of its own (YAGNI); otherwise generate it - explain the omission in the report.

### 3.3 Infrastructure (`demo/modules/<id>/infrastructure/`)
- `CurlRemoteServiceClient implements RemoteServiceClient`: PHP `curl_*` functions (no new Composer dependency - ask
  the user first if one seems needed, per generate-api's rule); base URL = `remote_service.emulator_url` in tests
  (config value, not hard-coded - AGENTS.md "do not assume... use `Module::getInstance()`/components"), `base_url` in
  production; `Content-Type: application/json`; timeout from a module config default; if
  `remote_service.signature.enabled` is `true`, add a documented extension point for the signing header/param and
  record in the report that the algorithm is undecided (CLAUDE.md) - never invent one.
- AR persistence models + repositories for extra tables - same pattern as `demo/infrastructure/persistence/ProcessRecord.php`/`ArProcessRepository.php` (AR never leaves this layer, no business logic in it).
- **Migrations** (`demo/modules/<id>/migrations/`, namespace `app\modules\<id>\migrations`, portable, no AR inside):
  1. `M<YYMMDDHHMMSS>RegisterService` - mandatory, exact body from AGENTS.md "Service registration":
     `insert('{{%service}}', ['name' => '<id>', 'created_at' => time(), 'updated_at' => time()])` in `safeUp()`,
     `delete('{{%service}}', ['name' => '<id>'])` in `safeDown()`.
  2. One migration per `migrations.extra_tables[]` item, table/columns/indexes/foreign_keys/records exactly as
     declared, `safeUp()`/`safeDown()` exact reverse (same shape as `demo/migrations/m..._add_service_registry.php`).
  Create with `php yii migrate/create <Name> --interactive=0` (`-w /app/demo`) for the timestamp, then write the body;
  apply with `php yii migrate --interactive=0`; verify `service` gets the `<id>` row and any extra tables match the
  spec (`SHOW CREATE TABLE`, through `docker compose exec mysql`, never print passwords).
- Wiring - `demo/config/web.php` → `container.singletons` (minimal `Edit`, keep everything else):
  `\app\modules\<id>\domain\RemoteServiceClient::class => \app\modules\<id>\infrastructure\CurlRemoteServiceClient::class`
  plus one entry per extra-table repository interface. **Do this in the module's own `Module::bootstrap()`** instead
  when the binding must not appear in host config at all - `AGENTS.md` "Module architecture" rule 6/"a module touches
  host files only to register itself"; prefer the module's own DI bindings inside `Module::bootstrap()` over editing
  `config/web.php`'s `container` for anything beyond the two mandatory config entries below.

### 3.4 Interface (`demo/modules/<id>/controllers/V1Controller.php`)
- `extends app\controllers\BaseController`; constructor takes the use cases of §3.2 via constructor injection (DI
  container, bound in `Module::bootstrap()`).
- Implements **only** the three abstract methods (AGENTS.md "Module architecture" rule 3):
  - `doProcess(string $type, Process $process, array $data): array` - `$type` is `'init'` or `'callback'`; dispatch on
    `$process` state / `$data` per the method's use case; never overrides `behaviors()`/`verbs()`/`actionInit()`/`actionCallback()`.
  - `getExternalId(array $data): string` - reads `callback.external_id_param` (per the method the callback belongs to;
    if methods disagree on the path, resolve the method first from the stored process, not from the callback body alone).
  - `getCallbackStatus(array $data): string` - `'success'|'process'|'fail'` via `StatusMapper`, never `'init'`/`'error'`.
- `Module.php`: `extends yii\base\Module implements yii\base\BootstrapInterface`; `bootstrap()` adds the module's URL
  rules via `yii\rest\UrlRule` (`controller => '<id>/v1'` - fully qualified, since `GroupUrlRule`'s own `prefix`
  rewrites only entries shaped `{pattern, route}`, which a `yii\rest\UrlRule` config is not - add it to the url
  manager directly, do not nest it inside a `GroupUrlRule`; `pluralize => false`, `extraPatterns` for `init`/
  `callback` plus any extra request from `module.yaml`) and any DI bindings kept local to the module (§3.3).
  **`extraPatterns` entries are verb-agnostic** (`'init' => 'init'`, never `'POST init' => 'init'`): `BaseController`
  already extends `yii\rest\Controller`, whose default `behaviors()` wires a `yii\filters\VerbFilter` from
  `BaseController`'s own `verbs()` (`['init' => ['POST'], 'callback' => ['POST']]`) - that is where verb enforcement
  and CORS-preflight (`OPTIONS`) handling belong. A verb-restricted URL pattern rejects every other verb at the
  **routing** layer, before the request ever reaches the controller/`VerbFilter` - the result is a bare 404 for a
  wrong verb and for an `OPTIONS` preflight alike (breaking real CORS in a browser), instead of `VerbFilter`'s
  correct `405` / preflight response. Verify after generating: `OPTIONS /<id>/v1/init` → `200` with `Allow`/CORS
  headers, `GET /<id>/v1/init` → `405` (not `404`).
- Class name `V1Controller` (one per API major version in `module.yaml` → `requests[].version`; generate one controller
  per distinct version if more than `v1` is declared).

## 4. Checks (per layer, must print nothing unless noted)
```bash
# domain + application: no Yii, no AR, no infrastructure
grep -rnE 'Yii::|use yii[\]|extends (ActiveRecord|Model|Component|BaseObject)|[\]infrastructure[\]' demo/modules/<id>/domain demo/modules/<id>/application
# AR only in infrastructure
grep -rln "extends ActiveRecord" demo/modules/<id> --include=*.php | grep -v "/infrastructure/"
# migrations apply and are reversible
MSYS_NO_PATHCONV=1 docker compose exec -T -w /app/demo php-cli php yii migrate --interactive=0
MSYS_NO_PATHCONV=1 docker compose exec -T -w /app/demo php-cli php yii migrate/down 1 --interactive=0   # RegisterService reversible
MSYS_NO_PATHCONV=1 docker compose exec -T -w /app/demo php-cli php yii migrate --interactive=0
```
- `service` table has a row with `name = '<id>'`.
- `V1Controller` defines only the three abstract methods (no `behaviors()`/`verbs()`/`actionInit()`/`actionCallback()` overrides).
- Every `callback_url` sent by `RequestBodyBuilder` equals `http://demo.dev/<id>/v1/callback`, never taken from `data`.
- `http://demo.dev/<id>/v1/init` and `.../callback` resolve (405 on GET, not 404); an unregistered id still 404s (Yii routing, before the URL rule adds it - N/A once registered).

## 5. Register and verify
1. `demo/config/web.php`: add `'<id>' => ['class' => \app\modules\<id>\Module::class]` to `modules` and `'<id>'` to
   `bootstrap` (minimal `Edit`).
2. `demo/config/console.php`: add `'app\modules\<id>\migrations'` to `controllerMap.migrate.migrationNamespaces`.
3. Unit tests (fakes, no database - snapshot-clone pattern of generate-api §"Tests"):
   ```bash
   MSYS_NO_PATHCONV=1 docker compose exec -T -w /app/demo php-cli sh -c 'vendor/bin/codecept build >/dev/null; vendor/bin/codecept run Unit --no-colors'
   ```
   All green; report the real counts (host + this module).
4. All §4 checks again; `http://demo.dev/` still answers 404 from Yii (routing untouched for other paths).

## 6. Independent review
Run skill **`design-review`** on the generated files in a separate pass (fresh subagent, maker ≠ checker). Fix errors;
fix warnings or explain why accepted; send fixes back for a re-check. A fix that changes behaviour a spec describes
updates the spec (`module.yaml`/`module.service.yaml`) in the same step, so spec and code stay equal - report the change.

## 7. Report
Module id and specs used; files generated/kept/differing per layer; migrations applied and the `service` row; wiring
edits; check and test results; review verdict with what was fixed; spec changes if any; open points carried over from
`module.service.md` §10 plus anything CLAUDE.md still lists as undecided; the next step: `generate-emulator` Part B,
then `test-module` (both run by `create-module` in the normal pipeline - when started by it, just return this report).

## Rules
- The specs (`module.yaml`, `module.service.yaml`) are the source of truth for data; the project rules (AGENTS.md,
  code-design, ddd-yii2) are the source of truth for how code is structured. A conflict between them is asked, not
  silently resolved either way.
- Never overwrite an existing file without the user's consent; never edit `vendor/`; never drop or alter tables outside
  this module's own migrations; never touch another module's files.
- No new Composer dependency without the user's approval (the remote-service client uses PHP curl by default).
- Nothing that CLAUDE.md lists as an open decision (authentication, signature algorithm, emulator scenario selection,
  emulator database) is decided here - record it as still open in the report.
- `callback_url` is always added by `RequestBodyBuilder`, never read from `data`, never omitted, never left to the
  remote-service client to add.
