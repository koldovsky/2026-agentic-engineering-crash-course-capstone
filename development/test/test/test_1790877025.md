## 8. Cross-cutting
- [x] X-01 CORS preflight `OPTIONS` on both endpoints is not rejected
  **Was a real defect, fixed in iteration 2.** Root cause: `Module::bootstrap()` registered URL rules as
  verb-restricted string patterns (`'POST v1/init' => ...`), so any other verb - including `OPTIONS` - never
  resolved to a route at all, never reaching `BaseController`'s `VerbFilter`/CORS filter. Same root cause as
  CB-05/INIT-06's 404-instead-of-405. **Fix**: switched `demo/modules/test/Module.php` (and, for consistency,
  `emulator/modules/test/Module.php`) to `yii\rest\UrlRule` with **verb-agnostic** `extraPatterns`
  (`'init' => 'init'`, not `'POST init' => 'init'`) added directly to the url manager (not nested in `GroupUrlRule`,
  whose `prefix` only rewrites `{pattern, route}`-shaped entries). Verb enforcement now correctly happens at the
  controller via `yii\rest\Controller`'s built-in `VerbFilter` (from `BaseController`'s own `verbs()`), which also
  handles `OPTIONS` correctly. Confirmed live: `OPTIONS /test/v1/init` → `200` with
  `Access-Control-Allow-Methods`/`Access-Control-Allow-Origin` headers; `GET /test/v1/init` → `405`; `POST` still
  `422`/`200` as before (full init flow re-verified end to end, 64 unit + 6 functional tests + PHPStan all still
  green on both apps). Propagated to `generate-module`/`generate-emulator`/`design-review` SKILL.md so future
  modules don't repeat it.

  Open - CLAUDE.md lists authentication as undecided; correctly left unchecked, not invented.
